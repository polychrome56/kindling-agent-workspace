# 具体、有逻辑地解释复杂问题

目标不是固定套用某一种模板，而是根据问题本身选择合适的组织方式，让用户建立一个可以复述、验证和迁移的心智模型。

## 何时使用

适合：

- 用户问“这个机制到底怎么实现”“从头带我走一遍”。
- 用户说“太抽象”“没看懂”“用真实例子讲”。
- 问题包含多个阶段、层次、参与者、状态或分支，容易混在一起。
- 用户知道局部事实，但不明白它们之间的因果关系。
- 需要结合真实代码、数据、现象或操作来验证原理。

不要强制用于：

- 一个定义、一条命令或一个确定事实就能回答的问题。
- 只需汇报结果或状态的问题。
- 用户只要求实现、修复或审查，且没有要求教学说明。
- 故障已经有明确报错和直接原因；先回答原因和修复，不要先写教程。

## 回答前

1. 先检查真实代码、数据或运行结果，不要仅凭常识补全实现。
2. 找出用户真正卡住的位置：不知道目标、不理解步骤、不理解原因，还是分不清相近概念。
3. 判断这个问题最适合按什么维度拆分，不要预设一定按时间或系统层次拆。
4. 选择一个足够简单、又能覆盖关键关系的实例。后文尽量使用同一个实例。
5. 判断哪些细节是理解主线所必需，哪些应该等用户理解主线后再展开。

## 核心组织方法

### 1. 先给一句可检验的结论

结论要直接回应疑问，并划清范围。必要时指出用户前提或上一轮解释中的问题。例如：

```text
是，但只发生在 A 条件下；正常情况主要依靠 B，C 只是信息不足时的补充手段。
```

如果前一轮解释混淆了概念，直接说明混淆在哪里，不要继续沿用错误前提。

### 2. 选择适合当前问题的拆分维度

先判断哪种关系最能解释当前问题，只选择主要的一到两个维度：

- **时间或流程**：事情先后怎样发生。
- **职责或层次**：谁负责什么，各部分怎样协作。
- **数据流向**：数据从哪里来，经过什么变换，到哪里去。
- **状态变化**：对象从什么状态变成什么状态。
- **因果关系**：什么条件导致什么现象。
- **决策分支**：不同条件分别走哪条路径。
- **结构组成**：整体由哪些部分组成，部分之间是什么关系。
- **对比维度**：两个版本、方案或概念究竟差在哪里。

例如：网络转发通常沿数据流讲；资源泄漏通常沿所有权和生命周期讲；版本差异通常先找变化点，再对比变化前后的执行路径。不要把某一次回答中的阶段划分当成通用模板。

### 3. 先给全局坐标，再放大局部

先用几句话或一张简单图说明：

- 当前讨论对象是什么；
- 它要完成什么目标；
- 用户卡住的部分位于整体的哪里。

然后只放大当前相关部分。不要一开始进入字段、指令或边界条件，让用户失去方向。

### 4. 说明“为什么需要”，再讲“怎么实现”

实现细节必须对应一个明确需求。优先使用：

```text
目标 → 遇到的困难 → 采用的办法 → 得到的结果
```

如果用户不理解某种设计，先解释它解决了什么限制；如果用户已经理解目的，再进入代码和数据。

### 5. 把大问题改写成有限的具体问题

子问题要共同覆盖用户的疑问，而不是机械罗列工具、文件或函数。可以从“要识别什么、信息从哪里来、怎样转换、结果怎样使用”开始，但应根据当前问题重新设计，不能固定套用。

### 6. 每一步形成完整因果链

根据复杂度显式或隐式回答：

1. **当前要解决什么**
2. **已知条件或输入是什么**
3. **为什么采用这个办法**
4. **具体怎样做**
5. **得到什么结果**
6. **这个结果接下来有什么用**

推荐表达：

```text
要找：对象在运行时的位置
已知：文件记录相对地址，进程提供加载基址
原因：地址随机化后不能直接使用文件地址
操作：相对地址加加载基址
结果：得到当前进程里的真实地址
用途：后续才能读取对应内存
```

不需要每次展示这些标签，但逻辑上不能缺项。

### 7. 区分事实、推导和示例

让用户知道关键结论的依据：

- **直接事实**：代码、文档、协议、数据或运行结果明确给出。
- **推导结果**：由若干事实计算或推理得到。
- **实现约定**：项目选择、版本常量或兼容规则。
- **简化示例**：为了说明关系而省略次要细节。
- **人工验证**：用于证明理解，不一定是正式实现采用的步骤。

存在主路径和例外时，先讲主路径，再说明例外为什么存在。不要用例外打断主线。

### 8. 用一个实例完成闭环

实例应从问题起点走到用户能识别的结果，不要只举半截例子。根据问题选择真实进程、数据包、请求、对象、调用、代码输入、日志或计算结果；无法运行时，使用明确标注的最小假设实例。

实例要贯穿解释，不要每节更换人物、数字或对象。具体值旁边保留语义。

### 9. 图只表达一种主要关系

- 流程关系：使用有方向的步骤图。
- 内存关系：使用地址、偏移和指针图。
- 调用关系：使用调用树。
- 结构关系：使用包含和引用图。
- 分支关系：使用决策图。
- 对比关系：使用并列路径。

一张图不要同时表达时间顺序、内存布局和版本差异。短 ASCII 图通常比大型 Mermaid 图更适合逐步教学。

### 10. 逐层增加细节

通常遵循：

```text
一句结论 → 整体关系 → 一个实例 → 关键实现 → 必要例外
```

如果用户只卡在某一步，保留一句整体坐标后，只放大这一步。不要因为可以继续讲，就一次展开所有相关知识。

### 11. 代码和工具用于证明，不用于组织答案

引用最小范围的真实代码，并在引用前说明它证明什么。优先引用：

- 关键入口和调用关系；
- 决定行为的条件；
- 数据或状态的来源；
- 主路径与例外路径的分界。

不要按“执行了哪些命令、打开了哪些文件”组织答案。工具是取证手段，不是系统原理。

### 12. 最后压缩成可复述模型

结尾用三到五句话重新串起最关键的因果关系。摘要应随问题变化，不使用固定文案。如果仍有后续内容，只指出紧邻主线的下一步。

## 详细程度控制

- 用户第一次问：先给整体关系和一个闭环实例。
- 用户指出某一步不懂：只放大这一段，同时保留它在总流程中的位置。
- 用户已经理解原理：进入真实结构、数据、代码或操作验证。
- 用户要求从头学习：可以详细，但每一节都要回答一个明确问题。
- 用户只问“是否如此”：先直接回答是/否，再补必要边界。

详细不等于把所有细节一次讲完。新概念只有在当前步骤马上要用时才引入。

## 自检

回答前检查：

- 是否直接回答了用户当前疑问？
- 是否选择了适合这个问题的拆分维度，而不是套用熟悉模板？
- 用户能否知道当前局部位于整体的哪里？
- 是否讲清了“为什么”，而不只是“怎么做”？
- 是否始终使用同一个实例？
- 关键结论是否有事实、推导或代码支持？
- 是否区分了主路径、例外和人工验证？
- 图中的箭头是否能用一句话解释？
- 删除任一节后若不影响主线，该节是否应暂缓？
- 用户读完后，能否用三到五句话复述整个流程？

## 禁止做法

- 不要把“工具执行顺序”当成“系统工作原理”。
- 不要用大量术语替代因果关系。
- 不要预设所有问题都应该按时间、层次或某个特定技术流程拆分。
- 不要把回退方案描述成所有环境都会执行的主路径。
- 不要为了显得完整而展开与当前疑问无关的缺陷、优化和版本历史。
- 不要机械套用固定标题；问题简单时保持简短。
