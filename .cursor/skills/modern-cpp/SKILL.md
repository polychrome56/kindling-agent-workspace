# Modern C++

这个 skill 只处理 C/C++ 的专项工作流：重构、设计取舍、模式选择、性能/并发排查和学习讲解。常驻工程红线由 `cpp-engineering.mdc` 负责，这里不重复展开。

不要主动联网搜索资料或泛泛引用外部项目；除非用户明确要求，否则直接按下面的流程给出判断和改动。

## 快速流程

1. 先读相关 `.h/.cpp`、调用方、构建入口和测试入口。
2. 判断任务类型：重构、设计审查、性能/并发、学习讲解、实现辅助。
3. 先给结论：当前主要风险是什么，推荐走哪条路径。
4. 再给最小改法：优先小步修改，避免一上来大重构。
5. 完成后运行最小可用验证；不能验证时说明原因和风险。

## 任务流程

实现新功能：

- 先找已有相近实现和调用方。
- 新增最小接口，不先设计完整框架。
- 对系统边界依赖保留可替换点，方便后续测试。

重构旧代码：

- 先列出具体问题：重复、长函数、职责混乱、生命周期不清、错误处理不一致、测试困难。
- 优先提取纯函数和边界封装，再改类结构。
- 每次重构都要能解释收益、能编译、能回滚。

学习讲解：

- 先说明当前代码哪里不理想。
- 再说明成熟写法通常怎么做。
- 最后给出一小步可执行改进，不只讲概念。

设计审查：

- 先画出当前职责边界：谁创建、谁拥有、谁调用、谁释放。
- 找出隐藏依赖、跨层调用、全局状态、生命周期不清和测试障碍。
- 给出 1 个推荐方案；只有差异明显时才列备选方案。

## 设计模式选择

只有变化点明确时才引入模式。先回答：变化点是什么？谁拥有资源？测试是否需要替换实现？

- Strategy：同一流程中需要替换算法或策略。
- Factory：对象创建复杂，或生产/测试需要创建不同实现。
- Adapter：隔离系统命令、第三方库、内核接口或旧接口。
- Dependency Injection：依赖需要在测试中替换，或不应由类内部偷偷创建。
- PIMPL：头文件暴露太多实现细节，或需要降低编译依赖。
- Observer：确实存在多个订阅方；必须设计注销和生命周期。

- 为单一实现创建抽象基类。
- 用 Singleton 隐藏全局状态。
- 用继承表达“有一个”关系；优先组合。
- 为了“设计模式”增加间接层、动态分配或虚调用。

## 并发与性能

- 先确认共享状态和线程模型，再改锁。
- 用 `std::lock_guard`、`std::unique_lock`、RAII guard 管理锁生命周期。
- 原子变量只用于清晰的同步语义；不要用 `volatile` 替代同步。
- 性能改动前先找证据：profile、benchmark、计数器、日志或可复现实验。
- 如果无法测量，优先做明显的低风险改进，不做复杂优化。

## 输出要求

- 做设计/重构建议时，按“问题 -> 建议 -> 代价/风险 -> 验证方式”组织。
- 做学习讲解时，按“当前写法 -> 为什么有风险 -> 更好的写法 -> 一小步练习”组织。
- 做代码修改时，说明改了什么、为什么这样改、验证了什么。

## 最终检查

- 是否遵守 `cpp-engineering.mdc` 的所有权、RAII、错误处理、热路径和验证要求。
- 是否只解决当前变化点，没有引入预防式抽象。
- 是否给出了用户能学习和复用的理由，而不只是贴代码。
